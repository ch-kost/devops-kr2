# Ответы к защите КР2

1. Loopback контейнера относится только к его собственному сетевому пространству. Переадресация Docker приходит на контейнерный интерфейс, поэтому сервер на `127.0.0.1` её не принимает. `0.0.0.0` внутри контейнера делает процесс доступным на его интерфейсах, но не меняет публикацию порта хоста: `127.0.0.1:<порт>:<порт>` по-прежнему ограничивает вход loopback хоста.

2. Пароль шаблона раскрыт в опубликованной истории и больше не секретен. Его нужно отозвать/заменить новым случайным значением и не использовать повторно. Удаление файла новым коммитом недостаточно. Историю можно очистить специализированным инструментом, но переписывание уже опубликованной main требует координации с участниками и обновления их копий; оно не гарантирует удаления ранее сделанных копий секрета.

3. Образы многослойные. `RUN rm .env` скрывает файл в итоговой файловой системе, но предыдущий слой продолжает содержать его. Получивший образ из реестра может извлечь слой. Секрет исключают из build context, а необходимые при сборке секреты передают специальными механизмами BuildKit.

4. Exec-форма запускает Gunicorn непосредственно, без `/bin/sh -c`, что обеспечивает доставку сигналов и штатную остановку PID 1. Проверки: `docker compose top` и `docker compose exec app ps -o pid,ppid,user,args` (если ps установлен); без ps можно читать `/proc/1/cmdline` и `/proc/1/status`.

5. `${REDIS_PASSWORD}` подставляет Compose на хосте при чтении конфигурации. `$$REDIS_PASSWORD` превращается в `$REDIS_PASSWORD` для последующего раскрытия оболочкой внутри контейнера во время healthcheck. Если использовать `${...}` в проверке, секрет будет заранее вписан в конфигурацию команды и может не совпасть с env_file при экспортированной переменной оболочки. Обёртка `scripts/compose.sh` снимает такую неоднозначность через unset.

6. Точка входа официального Redis распознаёт `redis-server`, подготавливает права данных и понижает привилегии до redis. При `sh -c` специальная ветка может не сработать и Redis останется root. Проверяют `docker compose top` и `/proc/1/status` из контейнера: UID должен отличаться от 0.

7. Отсутствие host-публикации не ограничивает взаимодействие внутри Docker-сети. К Redis может подключиться приложение и другой участник этой сети, включая скомпрометированный контейнер. Пароль добавляет проверку подлинности, но не заменяет сетевую изоляцию и контроль доступа к Docker.

8. Обычный depends_on задаёт порядок запуска контейнеров, но не готовность сервиса. `condition: service_healthy` ждёт успешного PING Redis. Без ожидания первые запросы приложения могут завершаться ошибкой соединения с ещё не запущенным Redis.

9. `docker compose down` удаляет контейнеры и сеть, сохраняя именованный том, поэтому следующий запуск продолжает счётчик. `down -v` удаляет и том, и данные. Смена тега сама по себе том не удаляет, но `redis:latest` может принести несовместимую основную версию или формат данных, поэтому обновление требует проверки совместимости и резервной копии.

10. Отдельный сертификат содержит SAN нужного имени и отделяет ресурс КР2 от прежнего сайта. Отдельный самоподписанный `kr2.crt` не будет доверенным при `--cacert devops.crt`; curl сообщит ошибку цепочки/доверия. Nginx выбирает сертификат во время TLS handshake по SNI; если имя не передано или не найдено, используется default server соответствующего адреса/порта.

11. `client` содержит `X-Real-IP`, который Nginx установил равным своему `$remote_addr`. При проверке это адрес клиента, видимый Nginx; он зависит от реальной топологии и не должен выдумываться заранее. TCP-партнёр Flask — прокси, а не исходный клиент. Клиент сам может прислать ложный X-Forwarded-For; доверять можно только заголовкам от ограниченного доверенного прокси и правильно разобранной доверенной цепочке.

12. В VM автоматически запустятся только включённые systemd-службы. При включённых Docker и nginx запустятся nginx и контейнеры с `restart: unless-stopped`, кроме остановленных вручную. Сам запуск VM после перезагрузки физического хоста зависит от гипервизора. Разовые тестовые контейнеры без restart policy и вручную запущенные процессы не восстановятся автоматически.

13. Браузер/curl хоста должен превратить домен в Host-only IP, поэтому hosts нужен на хосте. Сервер выбирает server block по Host/SNI и соединяется с `127.0.0.1:<порт>`; собственное DNS-разрешение имени сайта при такой конфигурации ему не требуется.

14. Публикация без host-IP открывает порт на всех адресах хоста. Docker создаёт NAT/forwarding-правила, и трафик может пройти мимо обычных UFW INPUT-ограничений. Проверка только состояния UFW либо наличия Docker не обнаружит ошибочную публикацию; нужно отдельно проверять результат `docker compose port app <порт>` строго на `127.0.0.1:<порт>` и отсутствие публикации Redis. Готовый audit-kr2.sh выполняет такую проверку. Точный состав старого раздела [5] должен быть сопоставлен с реальным scripts/audit.sh из ПР №7.
